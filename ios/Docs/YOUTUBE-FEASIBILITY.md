# YouTube 独立解析（iPhone 本地）技术可行性评估

日期：2026-10-28 · 结论先行：**当前版本不支持，且不伪装支持。**
范围声明：本评估仅针对用户**自有或获授权**的内容；不涉及任何 DRM 绕过或
访问控制规避（这类能力无论如何都不会被实现）。

## 1. 逐项评估

### 1.1 iOS 本地解析器是否可维护 —— 不可行
- 业界事实标准 yt-dlp 是 Python 工程（约 4000+ 文件的提取器），依赖 CPython
  运行时，无法在 iOS App 沙箱内合法分发运行。
- 纯 Swift/ObjC 的第三方"youtube-dl 移植"几乎全部处于停止维护状态
  （YouTube 每次变更播放器签名/客户端接口都会使其失效）。
- 结论：自研维护成本 ≫ 收益，短期不可维护。

### 1.2 第三方解析组件的系统兼容性 —— 差
- App Store 审核 2.5.2（不得下载可执行代码）限制了"运行时加载解析脚本"类方案。
- 解析组件需要频繁更新，而 App Store 审核周期使更新滞后 1–7 天——
  意味着每次 YouTube 变更后 App 将有数天不可用窗口。

### 1.3 JavaScript 运行依赖 —— 理论可行，工程上脆弱
- iOS 有系统级 JavaScriptCore，理论上可执行 YouTube 网页播放器的
  签名解算逻辑（sig_decipher）。开源社区有此类尝试。
- 但：该逻辑随播放器版本随机化，需持续逆向维护；且爬取非公开接口
  与 YouTube 服务条款冲突，存在账号/法律风险。
- 结论：不作为产品能力交付。

### 1.4 音视频分离（DASH）处理 —— 可行但重
- YouTube 高画质流是音视频分离的（webm/m4a + 独立音轨），需要：
  下载两路流 → 本地合并（FFmpeg 或 AVFoundation 混流）。
- iOS 端 AVFoundation 可做 m4a+mp4 混流（无转码），FFmpeg 移植体积大
  （>30MB），两者都显著增加复杂度与功耗。

### 1.5 来源更新导致解析失效的风险 —— 高
- YouTube 变更频率：客户端 API/播放器签名平均每月数处变化。
- 无官方下载 API 允许第三方获取用户自有视频的原始流。

### 1.6 iOS 内存与后台限制 —— 中等压力
- 单路视频流下载本身无压力；压力在"多格式探测 + 多路并发拉流 + 合并"。
- 后台 URLSession 适合整文件下载；YouTube 的流 URL 有时效（约 6 小时）
  且需先解析，后台长任务与解析时效叠加后成功率进一步下降。

### 1.7 是否存在不依赖个人 Windows 电脑的方式 —— 有，但各有代价

| 路径 | 独立性 | 代价 / 风险 |
| --- | --- | --- |
| **A. YouTube Studio 官方下载**（用户自己的视频） | ✅ 完全独立 | 仅限自己的频道；官方导出的原始文件；零风险。**推荐首选** |
| B. iOS 端 JavaScriptCore 自研解析 | ✅ 独立 | 高维护成本 + ToS 冲突 + 审核风险；不推荐近期投入 |
| C. Windows 端 yt-dlp 解析 → 局域网传输给 iPhone（Phase 4 协同） | ❌ 依赖电脑在线 | 电脑必须开机；但工程可靠、法律边界清晰（用户对内容授权自负） |
| D. 自建云服务器跑解析（替代 Windows） | ✅ 不依赖个人电脑 | 需要服务器与费用；等同把"C"的机器搬到云端，授权责任同样在用户 |

## 2. 当前产品决策（v0.1）

1. iOS App 内 YouTube 链接 → 明确提示"未支持"，展示本报告要点与替代路径，
   **绝不静默失败、绝不伪造下载**。
2. 用户自有内容推荐路径 A；电脑在线时可用路径 C（Phase 4）。
3. Windows 端解析能力只声明为 Windows 功能；iOS 端任何"来自 Windows 的任务"
   都会明确标注任务来源为"Windows 协同"，与本地任务区分显示。

## 3. 重新评估的触发条件

- YouTube 提供官方授权的第三方下载 API；或
- 出现可长期维护的独立解析组件（>6 个月持续跟进 YouTube 变更的开源项目）；
  任一条件满足时重启本评估。
